# نظام إدارة الزكاة والتبرعات — V12.0.0

نسخة موحدة كاملة بواجهة عربية RTL وSupabase، تشمل العمليات النقدية والعينية، تخصيصات الموزعين، ترخيص الأجهزة، Excel، التدقيق، النسخ الاحتياطي والاستعادة الحية، ومساعد Gemini بأدوات آمنة ومؤكدة.

## محتويات الحزمة

- `supabase/database_complete.sql`: ملف قاعدة البيانات الوحيد؛ يتضمن المخطط وRLS والدوال والحماية والنسخ الاحتياطي وجداول المساعد.
- `supabase/functions/`: وظائف `create-user` و`reset-user-password` و`gemini-assistant`.
- `js/` و`css/` و`index.html`: واجهة النظام القابلة للنشر على Vercel أو أي استضافة ثابتة.
- `tests/`: اختبارات الحالات والحسابات وعقود الأمان.
- `docs/`: دليل النشر والنسخ الاحتياطي والتقرير الفني.

لا توجد ملفات SQL إضافية أو ملف منفصل لأول مدير.

## تثبيت جديد على Supabase

1. أنشئ مشروع Supabase جديدًا، ثم افتح SQL Editor ونفّذ `supabase/database_complete.sql` كاملًا مرة واحدة. الملف مخصص للتثبيت النظيف؛ لا تنفذه كاملًا فوق مخطط قديم.
2. من Authentication أنشئ أول مستخدم بالبريد الداخلي `uXXXXXXXXX@zakat.local`؛ استبدل `XXXXXXXXX` برقم الهاتف اليمني المكون من 9 أرقام، وحدد كلمة مرور قوية.
3. من SQL Editor نفّذ هذا الاستدعاء مرة واحدة، مع تغيير الرقم والاسم:

   ```sql
   select public.bootstrap_first_admin('777123456','مدير النظام الأول',null);
   ```

   أول جهاز يسجل به أول مدير يُعتمد تلقائيًا، وكل جهاز لاحق يحتاج موافقة المدير.
4. عدّل `js/config.js` وضع رابط المشروع ومفتاح anon/publishable فقط. لا تضع مفتاح secret/service role ولا مفتاح Gemini في الواجهة.
5. انشر Edge Functions:

   ```bash
   supabase functions deploy create-user --no-verify-jwt
   supabase functions deploy reset-user-password --no-verify-jwt
   supabase functions deploy gemini-assistant --no-verify-jwt
   ```

6. أضف سر Gemini من بيئة آمنة:

   ```bash
   supabase secrets set GEMINI_API_KEY="YOUR_KEY"
   supabase secrets set GEMINI_MODEL="gemini-3.6-flash"
   ```

   يمكن تغيير النموذج بالسر دون تعديل الواجهة. وظائف Edge تدعم مفاتيح Supabase القديمة `ANON/SERVICE_ROLE` والمفاتيح الجديدة `PUBLISHABLE/SECRET`.
7. انشر مجلد المشروع كاستضافة ثابتة، ثم سجل الدخول بالهاتف وكلمة المرور.

## الترقية من V11

حسابات Auth مرتبطة بمعرّفات UUID، لذلك لا تنقل نسخة JSON وحدها إلى مشروع فارغ. المسار الآمن:

1. خذ نسخة مشروع Supabase كاملة ونسخة ZIP من داخل النظام القديم.
2. استنسخ/استعد المشروع الكامل في مشروع أو فرع تجريبي بحيث تبقى مخططات `auth` ومعرّفات المستخدمين.
3. في `supabase/database_complete.sql` ابحث عن علامة `V12.0.0 — single-database reliability`، ونفّذ من هذه العلامة حتى نهاية الملف على النسخة التجريبية فقط. هذه هي كتلة الترقية المتصلة داخل ملف القاعدة نفسه.
4. انشر الواجهة ووظائف Edge الجديدة، ثم افتح الإعدادات ← النسخ الاحتياطي لاختبار نسخة V11 أو V12 على المشروع المستنسخ.
5. V12 يتحقق من SHA-256. نسخة V11 القديمة غير موقعة، لذلك يسجل النظام تحذيرًا وتدقيقًا، لكنه يطبق قائمة جداول ثابتة وفحص صلاحية المدير والجهاز.
6. كتلة ترقية V12 نفسها معاملة ذرّية واحدة، والاستعادة دمج ذري كذلك: إما تنجح الجداول وفحوص التكامل كلها أو يتراجع PostgreSQL عن العملية كاملة.
7. طابق الأرصدة والتقارير واختبر كل دور، ثم خطط التبديل إلى النسخة المحدثة.

الاستعادة التطبيقية تخص بيانات الأعمال في المشروع نفسه. النسخة الكاملة لـ Auth وStorage وإعدادات المشروع وEdge Functions تؤخذ من Supabase Dashboard أو CLI؛ راجع `docs/BACKUP_AND_RESTORE.md`.

## الإصلاحات الرئيسية

- يولّد PostgreSQL رقم التحويل بين الصناديق تلقائيًا وبشكل آمن مع الطلبات المتزامنة، ويزامن العدّاد مع الأرقام القديمة عند الترقية، ويسمح للمدير والمشرف والمحاسب بإنشاء المسودة وفق RLS، ويتحقق من نشاط الصندوقين وتطابق العملة والرصيد قبل القيد المزدوج.
- لكل موزع خيار مستقل `يسمح له بإضافة مستفيدين جدد`. ملف الموزع الجديد يُربط به تلقائيًا ويبدأ تحت المراجعة؛ لا يستطيع الموزع اعتماده أو تغييره.
- بحث المستفيد في سند الصرف تلقائي، وRLS لا يعرض للموزع إلا مستفيديه. الموزع والصندوق والعملة تحدد من السياق الصحيح ولا يستطيع الموزع تعديلها.
- التسوية تحفظ `settled_return_amount` الخاص بها. إعادة الفتح تطرح هذا الجزء وحده من المرتجع وتعيد الرصيد المتبقي، دون المساس بأي مرتجع يدوي، وتُرفض إذا كان المبلغ قد أُعيد تخصيصه. إلغاء صرف بعد التسوية يبقي علامة التسوية والحسابات متوازنة.
- أزرار التشغيل تعرض حالتها الفعلية وتستخدم آلة حالات صريحة للمستفيد والتخصيص والجهاز، وعمود `is_active` لبقية الأدلة، مع رمز احتياطي عند تعذر تحميل مكتبة الأيقونات.
- زر إعادة المحاولة يعيد نتيجة الصرف أو الرسالة الفاشلة فقط إلى قائمة الانتظار، ولا يكرر عملية ناجحة.
- يسمح وضع عدم الاتصال بحفظ المسودات المسموح بها فقط؛ يمنع الخادم الترحيل النهائي دون اتصال حتى لا تعتمد عملية على رصيد قديم.
- المستند المرحل أو الملغي محمي من التعديل والحذف المباشر؛ الترحيل والإلغاء والعكس يتم عبر RPC ذرّي ومفاتيح منع التكرار.
- تقرير تكامل مالي يفحص الأرصدة السالبة وحدود التخصيص ومطابقة المصروف، وقيود القبض والتمويل، والتحويل ذي القيدين، واكتمال قيود العكس للمستندات الملغاة، وتطابق عملات الدفتر والحملات، ودفتر الصندوق والمخزون.

## المساعد الذكي

المساعد يعمل داخل Edge Function، لذلك `GEMINI_API_KEY` لا يصل إلى المتصفح. يدعم:

- البحث والملخصات وأرصدة الصناديق والحملات والموزعين.
- دليل داخلي رسمي لقواعد الحسابات والتسويات والصلاحيات والمخزون والنسخ الاحتياطي والأجهزة، كي لا يخمّن Gemini طريقة عمل النظام.
- كشف حساب المستفيد أو المتبرع أو الموزع أو الحملة.
- تقارير العمليات المعلقة وفحص التكامل المالي حسب الدور.
- اقتراح إنشاء مستخدم أو مدير أو موزع أو مستفيد أو متبرع أو حملة أو تحويل.
- اقتراح ترحيل سندات محددة أو تسوية/إعادة فتح تخصيص أو تغيير حالة سجل.

لا توجد أداة SQL حرة. كل قراءة تمر بصلاحيات المستخدم وRLS. أي تغيير يُحفظ أولًا كطلب `pending` لمدة محدودة، ويحتاج تأكيدًا مستقلًا في الواجهة، ثم يُنفذ مرة واحدة ويُسجل في التدقيق. كلمة المرور المؤقتة للمستخدم الجديد تُولد بعد التأكيد ولا تُرسل إلى Gemini ولا تُحفظ في سجل الإجراء.

خدمة Gemini خارجية وقد تتعرض لانقطاع أو حدود استخدام؛ النظام يعيد المحاولة للطلبات المؤقتة ويعرض رقم طلب وخطأ آمنًا، بينما تبقى القيود المالية داخل PostgreSQL ولا تعتمد على نجاح النموذج.
عند استخدام المساعد تُرسل صيغة السؤال والحد الأدنى من نتائج الأدوات اللازمة للإجابة إلى Gemini؛ لا تضع كلمات مرور أو مفاتيح API أو أسرارًا في المحادثة.

## المعادلات المعتمدة

- رصيد الصندوق = الرصيد الافتتاحي + الدائن − المدين.
- رصيد الحملة التشغيلي = التمويل المرحل − الصرف المرحل.
- متبقي الموزع = المخصص − المصروف − المرتجع.
- المتاح للصرف = الأقل بين رصيد الحملة التشغيلي ومتـبقي تخصيص الموزع.
- رصيد المخزون = الوارد الصالح − الصادر غير المعكوس، مع منع السالب والصرف حسب الأقدم صلاحية.

المسار النقدي: قبض في الصندوق ← تمويل الحملة ← تخصيص الموزع ← صرف للمستفيد.

المسار العيني: قبض في المخزن العام ← تمويل مخزون الحملة ← صرف سلة أو أصناف للمستفيد.

## الاختبار

من جذر المشروع:

```bash
node --test tests/*.test.mjs
```

راجع `docs/QA_REPORT_V12.md` لنتائج الفحص وحدود ما يمكن إثباته دون مشروع Supabase تجريبي. قبل الإنتاج نفّذ قبولًا كاملاً على مشروع منفصل، ثم اختبر نسخة احتياطية واستعادتها ومطابقة التقارير.

## الوضع التجريبي المحلي

غيّر `demoMode` إلى `true` في `js/config.js` ثم شغّل:

```bash
python3 -m http.server 8080
```

وافتح `http://localhost:8080`. بيانات العرض محلية ولا تعدّل Supabase، والمساعد يعرض ملخصًا محليًا فقط؛ Gemini والإجراءات الفعلية تحتاج الاتصال الحي.
