# تقرير التحقق — V12.0.0

تاريخ الفحص: 2026-08-15

## فحوص آلية منفذة

- فحص صياغة جميع ملفات JavaScript بـ `node --check`.
- فحص صياغة Edge Functions TypeScript بـ Node مع إزالة الأنواع تجريبيًا.
- 16 اختبارًا آليًا للحالات والحسابات والعقود الأمنية، وكلها ناجحة.
- توازن فواصل `$$` وعدد معاملات `BEGIN/COMMIT` في ملف SQL الوحيد، وأن كتلة V12 من علامتها إلى النهاية معاملة واحدة.
- تحقق ثابت من وجود توليد رقم التحويل ومزامنة عدّاده، وصلاحية الموزع، وسياسات RLS للتحويل والمستفيد والدفتر، وعكس التسوية، وحماية المستندات والحالات، والاستعادة الموقعة بما فيها دفتر الصناديق، وتوافق نسخ V11، وفحص التكامل.
- تحقق أن كل View وRPC تستخدمه الواجهة موجود في ملف القاعدة الوحيد وممنوح في قسم الصلاحيات النهائي.
- مطابقة بيانات العرض: مصروف كل تخصيص مع سندات الصرف المرحلة، والتحويل مع قيدي الصادر والوارد، وعدم وجود رصيد أو مخزون سالب.
- تحقق من عدم وجود `GEMINI_API_KEY` أو `service_role/secret` في ملفات الواجهة.

أمر إعادة الاختبار:

```bash
node --test tests/*.test.mjs
```

## سيناريوهات يجب قبولها على مشروع Supabase تجريبي

| السيناريو | النتيجة المطلوبة |
|---|---|
| إنشاء تحويل دون رقم يدوي | ينشأ رقم `CT-YYYY-NNNNNN` ثم يرحل بقيدين متساويين |
| ترقية وبها أرقام تحويل قديمة | يبدأ العدّاد بعد أكبر لاحقة رقمية بلا تعارض فريد |
| صندوقان بعملتين مختلفتين | رفض قبل الحفظ/الترحيل |
| موزع بلا صلاحية إضافة | لا يظهر زر الإضافة ويرفض RLS الإدخال المباشر |
| موزع بصلاحية إضافة | ينشأ المستفيد تحت المراجعة وبالموزع نفسه |
| بحث المستفيد كموزع | تظهر الملفات المعتمدة المرتبطة به فقط |
| تسوية تخصيص فيه متبقٍ | ينتقل المتبقي إلى مرتجع التسوية ويصبح صفرًا |
| إعادة فتح التسوية | يعود مرتجع التسوية فقط إلى المتبقي |
| إعادة فتح بعد إعادة تخصيص المرتجع | رفض واضح دون جعل رصيد الحملة سالبًا |
| إلغاء صرف بعد تسوية موزع | يبقى التخصيص متزنًا وتدخل القيمة في مرتجع التسوية القابل للعكس |
| تكرار الترحيل أو تأكيد AI | لا يتكرر القيد أو السجل |
| استعادة V12 معدلة يدويًا | رفض بسبب SHA-256 دون أي تغيير |
| استعادة السندات ودفتر الصناديق | تعود السندات وقيودها المرجعية ثم تنجح المطابقة المالية |
| استعادة V11 بلا أعمدة V12 الجديدة | تستخدم القيم الافتراضية ولا تفشل بسبب `NULL` |
| فشل فحص مالي بعد الاستعادة | تراجع كامل للمعاملة |
| انقطاع Gemini/429/5xx | إعادة محاولات محدودة ثم خطأ آمن بلا تنفيذ جزئي |
| إجراء AI حساس | يبقى pending حتى التأكيد ويظهر في التدقيق |

## حدود التحقق

لم تتوفر في بيئة البناء الحالية قاعدة PostgreSQL/Supabase تجريبية مخصصة يمكن الكتابة عليها أو محرك Chromium مثبت، لذلك لم يُنفذ ملف SQL فعليًا على مشروع حي، ولم تُجرَ مكالمة Gemini حقيقية بمفتاح مستخدم، ولم يكتمل اختبار واجهة آلي بمتصفح. الاختبارات الحالية تركيبية وحسابية وثابتة وليست شهادة تشغيل إنتاجي بنسبة 100٪.

قبل الإنتاج يجب تنفيذ جدول القبول أعلاه على مشروع منفصل، واختبار RLS بكل دور، ثم أخذ نسخة واستعادتها ومطابقة الأرصدة. لا يمكن لأي برنامج منع انقطاع خدمة خارجية تمامًا؛ التصميم يمنع أن يتحول فشل Gemini إلى تعديل غير مؤكد أو نصف عملية مالية.
