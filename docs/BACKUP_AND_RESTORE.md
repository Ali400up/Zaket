# النسخ الاحتياطي والاستعادة — V12.2 / V3

## المكوّن الذي يجب نشره في Supabase

النسخ لا يستدعي RPC مباشرة من المتصفح في V12.2. المسار الفعلي هو:

`واجهة النظام → supabase/functions/backup-manager → دوال backup_v3_* الثابتة → staging/commit`

انشر الوظيفة بعد ربط Supabase CLI بالمشروع:

```bash
supabase functions deploy backup-manager
```

يجب أن تظهر وظيفة `backup-manager` في Edge Functions داخل لوحة Supabase. يضبط `supabase/config.toml` لها `verify_jwt = true`، ثم تعيد الوظيفة التحقق من المستخدم وتمرر `Authorization` و`x-device-fingerprint` إلى دوال V3 بصلاحية المستخدم نفسه. لا تستخدم `service_role` ولا تتجاوز RLS.

تقبل الوظيفة ثمانية إجراءات فقط: `start_export` و`export_part` و`finish_export` و`cancel_export` و`start_restore` و`stage_restore_part` و`preflight_restore` و`commit_restore`. أي اسم RPC أو جدول غير مسموح يرفض قبل الوصول إلى قاعدة البيانات.

## ما الذي تنسخه الحزمة؟

يوجد مستويان مختلفان، وكلاهما ضروري:

1. **نسخة V3 من داخل النظام:** بيانات الأعمال والأدلة والحملات والصناديق والقيود والمخزون والإعدادات. النسخة الإدارية تضيف سجلات الأجهزة والتدقيق والمساعد وقاعدة المعرفة.
2. **نسخة مشروع Supabase الكاملة:** قاعدة PostgreSQL بما فيها Auth، وStorage، وإعدادات المشروع، ووظائف Edge وأسرارها. تؤخذ من أدوات Supabase ولا يمكن لملف ZIP داخل التطبيق أن يحل محلها.

لا تحتوي نسخة التطبيق كلمات مرور Auth أو مفاتيح API أو أسرار Gemini أو ملفات Storage نفسها.

## متطلبات التشغيل

- مدير نظام بحساب نشط ومن جهاز معتمد.
- اتصال ثابت أثناء بدء الجلسة وتنزيل الأجزاء أو رفعها.
- مساحة كافية في المتصفح لحفظ ملف ZIP.
- اختبار الاستعادة أولاً في مشروع Supabase تجريبي مستنسخ يحافظ على معرّفات `auth.users`.

## إنشاء نسخة V3

1. افتح **الإعدادات ← النسخ الاحتياطي**.
2. اختر **بيانات الأعمال** للاستخدام الدوري، أو **نسخة إدارية** عند الحاجة إلى سجلات الأجهزة والتدقيق والمساعد.
3. فعّل **نسخة متسقة** للنسخة الرسمية؛ يوقف الخادم الكتابة مؤقتاً أثناء القراءة ويمنع نسخة تجمع مراجعتين مختلفتين للبيانات.
4. اضغط إنشاء النسخة وانتظر اكتمال جميع الجداول والأجزاء.
5. احفظ الملف في موقعين مؤمّنين، وسجّل التاريخ والنطاق والشخص الذي أنشأه.

كل طلب شبكة محدود الحجم. يقسم الخادم الجداول إلى أجزاء لا تتجاوز 150 صفاً و450,000 بايت UTF-8، ويخفض عدد الصفوف تلقائياً إذا كان أحد الجداول عريضاً. يحسب PostgreSQL SHA-256 من نص JSONB نفسه الذي تستلمه الواجهة، ثم تضع الواجهة `manifest.json` وملفات الأجزاء داخل ZIP وتتحقق من البصمة مرة ثانية. إذا تغيّرت البيانات أثناء نسخة غير متسقة يرفض الخادم الجزء أو الإنهاء، ويحرر قفل النسخة المتسقة عند النجاح أو الإلغاء أو الخطأ؛ ويبقى انتهاء تلقائي بعد 45 دقيقة كحماية أخيرة عند انقطاع الجهاز تماماً.

## فحص الملف قبل الاستعادة

المعالج يرفض الملف قبل لمس قاعدة البيانات إذا حدث أحد الآتي:

- صيغة أو إصدار مخطط غير مدعوم.
- مسار ملف غير آمن أو جدول خارج القائمة الثابتة.
- جزء مفقود أو مكرر أو أكبر من الحد.
- اختلاف SHA-256 أو عدد الصفوف.
- اختلاف مجموعة الحقول بين صفوف الجدول، حتى لا تُهمل حقول بصمت أثناء تحويل نسخة قديمة.
- نقص جدول أساسي أو مرجع مطلوب.
- انتهاء جلسة الرفع أو عدم تطابق المستخدم.

بعد رفع الأجزاء يشغّل الخادم فحصاً مسبقاً ويعرض النطاق والوضع والأعداد وفحوص التكامل. المشكلات المانعة تظهر بالأحمر وتمنع زر التنفيذ، أما التحذيرات ـ مثل كون الحالة الحالية غير متوازنة والنسخة قد تكون وسيلة إصلاحها ـ فتظهر بلون كهرماني. حتى مع التحذير لا يعتمد الخادم النتيجة إلا إذا نجح فحص التكامل بعد الاستعادة.

## طريقتا الاستعادة

### الدمج — الوضع الافتراضي

- ينشئ السجلات الجديدة ويحدّث السجلات المطابقة بالمفتاح الأساسي.
- لا يحذف سجلات أحدث غير موجودة في النسخة.
- يحتاج كتابة عبارة `MERGE-RESTORE` في خطوة التأكيد.

### الاستبدال المطابق

- يجعل جداول بيانات الأعمال المشمولة مطابقة للنسخة ويحذف الزيادات وفق ترتيب يحترم المفاتيح الأجنبية.
- مناسب للرجوع المقصود إلى لقطة سابقة بعد اختبارها، وليس خياراً يومياً.
- يحتاج مدير النظام وعبارة `EXACT-RESTORE` وتحذيراً صريحاً في الواجهة.
- ملفات المستخدمين تُدمج ولا تُحذف بهذا الوضع، لأن حسابات Supabase Auth ليست جزءاً من نسخة التطبيق. ويحافظ النظام دائماً على ملف المدير الذي ينفذ العملية وجهازه المعتمد حتى لا يقفل النظام على نفسه.

التنفيذ النهائي معاملة PostgreSQL واحدة. إذا أخفق إدراج أو مرجع أو فحص مالي تتراجع كل تغييرات الاستعادة، ثم تبقى الجلسة ونتيجة الخطأ قابلة للتتبع. إعادة إرسال طلب الإنهاء أو التنفيذ بعد نجاحه تعيد النتيجة السابقة ولا تكرر العملية. بعد فشل التنفيذ يلزم بدء جلسة جديدة، بينما يبقى الملف المفحوص في الشاشة لتسهيل المحاولة.

## نسخ V1 وV2 القديمة

يقرأ المعالج ملفات V1/V2 محلياً، يطبق قائمة الجداول المسموحة، ويقسم الصفوف حسب العدد والحجم، ثم يبني manifest V3 وبصمات أجزاء جديدة قبل رفعها. في V2 يعيد الخادم تركيب بيانات المصدر ويتحقق أيضاً من بصمة V2 الأصلية؛ أما V1 فغير موقعة تاريخياً، لذلك يعرض الخادم تحذيراً واضحاً ولا يخفي ذلك. لا تُنشئ النسخة القديمة حسابات Auth في مشروع فارغ؛ استعدها في مشروع مستنسخ يحفظ UUID للمستخدمين، ثم أنشئ فوراً نسخة V3 جديدة.

## ما بعد الاستعادة

1. شغّل تقرير التكامل المالي.
2. طابق إجمالي ثلاثة صناديق وثلاث حملات وثلاثة موزعين وعينة مستفيدين.
3. اختبر تسجيل الدخول والأجهزة والأدوار ووظائف Edge والمساعد.
4. افحص المرفقات وStorage منفصلاً.
5. أنشئ نسخة V3 جديدة من الحالة المستعادة وسجّل نتيجة الاختبار.

## نسخة Supabase الكاملة

استخدم النسخ المجدولة أو PITR بحسب خطة المشروع، أو أوامر Supabase CLI الموثقة لنسخ قاعدة البيانات. احتفظ أيضاً بإعدادات وظائف Edge وأسماء الأسرار في إدارة أسرار مستقلة. لا تضع قيمة `service_role` أو `GEMINI_API_KEY` داخل الحزمة أو المستودع.

## اختبار شهري موصى به

- إنشاء نسخة أعمال V3 متسقة ونسخة إدارية عند الحاجة.
- استعادة الدمج في مشروع تجريبي.
- استعادة مطابقة في مشروع تجريبي آخر مرة دورية.
- مطابقة التقارير وفحص التكامل وتسجيل الزمن والنتيجة والمراجع.
- التحقق من نسخة المشروع الكاملة وAuth وStorage ووظائف Edge.
- حذف النسخ المنتهية وفق سياسة الاحتفاظ، لا من جهاز المستخدم الوحيد.

## معالجة الفشل

- **تغيرت البيانات أثناء النسخ:** أعد المحاولة مع الوضع المتسق.
- **اختلاف البصمة:** لا تعدّل ZIP يدوياً؛ استخدم الملف الأصلي أو أنشئ نسخة جديدة.
- **انتهت الجلسة:** أعد بدء المعالج وارفع الملف من البداية.
- **انقطع المتصفح أثناء نسخة متسقة:** يحاول المعالج إلغاء الجلسة وتحرير القفل فوراً؛ وإذا انقطع الجهاز كلياً ينتهي القفل تلقائياً خلال 45 دقيقة.
- **فشل الفحص المالي:** لا تتجاوز الفحص؛ راجع التقرير والسجلات المشار إليها.
- **الوظيفة غير موجودة (404):** انشر `backup-manager` وتأكد أن اسمها مطابق لما في `js/config.js` وأن المشروع المرتبط بالـ CLI هو المشروع الصحيح.
- **401 أو جلسة غير صالحة:** أعد تسجيل الدخول، ولا تنشر `backup-manager` مع `--no-verify-jwt` ما دام إعداد V12.2 الافتراضي مستخدماً.
- **انقطاع Gemini:** لا يؤثر في النسخ أو الحسابات؛ المساعد يعرض الدليل المحلي، بينما النسخ V3 يعمل عبر `backup-manager` ودوال PostgreSQL.
